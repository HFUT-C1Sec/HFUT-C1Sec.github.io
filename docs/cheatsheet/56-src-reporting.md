## 一、漏洞报告核心结构

### 标准报告模板

```
┌─────────────────────────────────────────────────┐
│ 1. 漏洞标题   ── 简明扼要说明漏洞类型与影响      │
│ 2. 漏洞位置   ── URL、参数、请求方式             │
│ 3. 漏洞描述   ── 原理说明（非技术人员也能看懂）   │
│ 4. 复现步骤   ── 分步骤详细说明 + 截图           │
│ 5. 危害分析   ── 结合业务场景量化危害             │
│ 6. 修复建议   ── 可落地的具体修复方案             │
└─────────────────────────────────────────────────┘
```

### 完整报告示例

#### 漏洞标题

> **某电商平台用户订单信息越权查询漏洞（中危）**

#### 漏洞位置

```
https://api.shop.com/v1/order/detail
Method: GET
Parameter: order_id
```

#### 漏洞描述

```
在用户订单查询接口中，未对请求参数中的订单ID进行权限校验。
攻击者可通过修改订单ID遍历获取任意用户的订单信息，
包含收货地址、联系方式等敏感数据。
```

#### 复现步骤（附截图）

```
1. 使用普通用户A登录系统
2. 查看自己的订单，Burp拦截到请求：
   GET /v1/order/detail?order_id=10001
3. 将 order_id 修改为 10002
4. 返回了用户B的订单信息（截图如下）
```

#### 危害分析

```
该漏洞导致：
- 任意用户的收货地址、手机号、姓名等PII信息泄露
- 可批量遍历所有订单，影响全平台用户隐私安全
- 结合社工手段可进一步扩大攻击面
```

#### 修复建议

```
1. 在订单查询接口中增加用户身份与订单归属的关联校验
2. 实现"当前用户只能查询自己的订单"的逻辑
3. 部署WAF拦截异常的批量订单ID查询请求
```

## 二、报告撰写进阶技巧

### 2.1 截图规范

| 必须截图的内容 | 说明 |
|:---|:---|
| URL栏 | 证明漏洞发生的准确位置 |
| 请求包 | 展示修改的参数 |
| 响应包 | 展示漏洞利用效果 |
| 漏洞证明 | 弹窗、数据泄露、命令执行结果等 |

> 📸 关键步骤必须有截图，包含URL、请求包、漏洞效果，确保审核人员可复现。

### 2.2 危害量化方法

```markdown
## 危害证明

✅ 信息泄露漏洞：
- 泄露字段：手机号、姓名、身份证号、收货地址
- 影响范围：全平台 100万+ 用户
- 泄露数量：通过脚本遍历可获取10000+条订单数据

✅ 远程代码执行：
- whoami 输出：www-data
- 可查看 /etc/passwd
- 可读取数据库配置文件
```

### 2.3 漏洞分级参考

| 等级 | 典型漏洞 | 赏金参考 |
|:---|:---|:---|
| 🔴 **严重** | RCE、全量数据泄露、任意账户登录 | 5000-50000+ |
| 🟠 **高危** | SQL注入、文件上传、严重越权 | 2000-10000 |
| 🟡 **中危** | 普通越权、XSS、敏感信息泄露 | 500-3000 |
| 🔵 **低危** | 反射型XSS、弱口令、信息泄露 | 100-500 |
| ⚪ **信息型** | 目录遍历、版本信息泄露 | 50-100 |

### 2.4 提升漏洞等级的技巧

```
1. 组合多个低危 → 提升为高危
   - XSS + CSRF → 存储型XSS
   - 信息泄露 + 弱口令 → 系统入侵

2. 证明实际影响
   - 信息泄露：真实截图数据（打码）
   - RCE：执行命令的截图
   - SQL注入：数据库信息截图
```

## 四、SRC挖掘六大避坑指南

### 🚨 避坑1：不违规测试

```markdown
✅ 做：
- 严格在厂商授权范围内挖掘
- 只测试SRC明确列出的域名/IP
- 点到为止，证明危害即可

❌ 不做：
- 测试未授权资产（内部系统、未公开环境）
- DoS/DDoS攻击
- 恶意篡改数据
- 批量下载用户数据
```

> 某白帽因挖掘某银行未公开接口被追责，这是典型的合规失误。

### 🚨 避坑2：不提交误报漏洞

```
✅ 提交前反复复现，确认漏洞真实存在
❌ 工具扫到什么就提交什么（很多是误报）
```

### 🚨 避坑3：不泄露漏洞信息

```
✅ 漏洞未审核通过前：
- 不公开漏洞细节
- 不分享给他人
- 不在社交媒体讨论

❌ 避免被黑产利用，导致厂商追责
```

### 🚨 避坑4：不盲目爆破

```
✅ 测试弱口令时：
- 控制爆破频率（每秒1-2次）
- 使用小字典精准测试
- 用代理IP分散请求

❌ 高频爆破触发厂商风控 → IP被封禁
```

### 🚨 避坑5：不忽视低危漏洞

```
新手成长路径：
1️⃣ 低危漏洞（反射型XSS、弱口令）→ 建立信心
2️⃣ 中危漏洞（越权、信息泄露）→ 积累经验  
3️⃣ 高危漏洞（SQL注入、RCE）→ 冲击高赏金
```

### 🚨 避坑6：不依赖自动化工具

```
工具是辅助，不是主力！
- XSS扫描器 → 扫不到存储型XSS
- SQLMap → 扫不到二阶注入
- 漏扫工具 → 扫不到逻辑漏洞

核心漏洞（逻辑漏洞）必须手工测试！
```

## 五、SRC新手成长路线

### 阶段1（0-1个月）

```
目标：熟悉流程，建立信心
- 在DVWA/Pikachu靶场练习工具操作
- 提交低危漏洞（反射型XSS、弱口令）
- 熟悉SRC规则和报告格式
```

### 阶段2（1-3个月）

```
目标：稳定产出中危漏洞
- 重点挖掘逻辑漏洞（越权、支付）
- 熟练掌握工具联动（OneForAll+Xray+Burp）
- 积累漏洞提交经验，提升审核通过率
```

### 阶段3（3个月以上）

```
目标：冲击高危漏洞，提升赏金
- 尝试云原生、API安全等新兴漏洞
- 聚焦头部厂商SRC
- 形成自己的挖洞方法论
```

## 六、SRC挖掘核心心法

### 六个"不要急"

```
1. 不要着急出洞 → 先慢慢摸索厂商的各种信息
2. 不要着急测试 → 先分析每一个数据包的功能点
3. 不要着急放弃 → 挖1-2小时没收获很正常
4. 不要急于求成 → 一个站测一周也可能没大洞
5. 不要着急提交 → 反复验证确保可复现
6. 不要着急分享 → 审核通过前保密
```

### 五个"要"

```
1. 要细 → 挖SRC一定要细，慢慢分析每个功能点
2. 要看范围 → 不看厂商漏洞收录范围=白干
3. 要关注活动 → 新上线项目/活动漏洞好挖
4. 要整理 → 每挖一个点都记录，避免重复劳动
5. 要合规 → 点到为止，表明危害就停
```
